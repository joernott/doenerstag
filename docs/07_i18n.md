# 07 Internationalization and localization

## Supported languages

| Code | Language | Role                                                   |
| ---- | -------- | ------------------------------------------------------ |
| `en` | English  | Source language and fallback. Complete by definition.   |
| `de` | German   | Full translation shipped with the application.          |

Adding a language means adding one catalog file; no code changes are required.

## Language selection

The interface language is resolved in this order, first match wins:

1. The `doener_lang` cookie, if it names a supported language.
2. The browser's `Accept-Language` header, matched against the supported
   languages by primary subtag — `de-AT` and `de-CH` both resolve to `de`.
3. English.

Choosing a language from the title bar writes the cookie and re-renders without
a page reload.

## Where translation happens

Translation is a **frontend** concern. The backend does not localize.

- API responses carry stable machine-readable identifiers — error `code`,
  allergen `code`, tag `code`, contact type `code` — and the frontend maps them
  to display text.
- API error `message` fields are English developer-facing text. The frontend
  shows the translation for the error `code` and only falls back to `message`
  when no translation exists.
- Log output is English, always, regardless of the operator's locale.
- User-entered content — restaurant names, menu item names, descriptions,
  free-text modifications — is never translated. It is displayed as entered.

Seeded reference tables carry `name_en` and `name_de` columns anyway. Those are
a fallback for API consumers that do not have the frontend's catalog, and a
source of truth for the seed data's meaning. The frontend prefers its own
catalog, keyed on `code`.

## Catalog format

- One JSON file per language under `frontend/src/i18n/`, compiled into the
  bundle at build time. Nothing is fetched over the network at runtime.
- Keys are dotted and namespaced by area, e.g. `order.deadline.label`,
  `error.1003`, `allergen.gluten`, `contact_type.phone`.
- Plural forms use the ECMA-402 `Intl.PluralRules` categories, so
  `order.items.count` has `one` and `other` variants for both languages.
- A build-time check fails the build if the German catalog is missing a key that
  exists in the English one. Extra keys in German are a warning.
- Interpolation uses named placeholders: `"{count} items from {restaurant}"`.

## Formatting

All formatting uses the browser's `Intl` API with the resolved interface
language as the locale.

| Value          | Rule                                                                                   |
| -------------- | -------------------------------------------------------------------------------------- |
| Dates          | `Intl.DateTimeFormat` with the interface locale. `en` → `Sep 10, 2026`, `de` → `10.09.2026`. |
| Times          | `Intl.DateTimeFormat`. `en` → 12-hour, `de` → 24-hour, as the locale dictates.          |
| Relative times | `Intl.RelativeTimeFormat` for deadline hints — "in 2 hours" / "in 2 Stunden".            |
| Weekdays       | `Intl.DateTimeFormat` weekday names, for opening hours.                                 |
| Numbers        | `Intl.NumberFormat`. Decimal and grouping separators follow the locale.                 |
| Money          | See below.                                                                              |

### Time zones

Every timestamp crosses the API as UTC (RFC 3339 with `Z`). The browser converts
to the viewer's local time zone for display, and converts back to UTC before
sending. The specification assumes restaurant and participants share one time
zone, so no time zone is ever displayed or stored alongside a timestamp.

Opening hours are wall-clock `time` values without a date and are displayed as
stored, without conversion.

### Money

Money is the one place where the interface locale does **not** decide
everything.

- The **currency** comes from the restaurant and never changes with the
  interface language. A restaurant priced in CHF shows CHF to a German-speaking
  and to an English-speaking user alike.
- The **number formatting** follows the interface locale.
- The symbol comes from the `currency` table's `symbol` column, and the number
  of decimals from its `minor_unit` column.
- Rendering uses `Intl.NumberFormat(locale, { style: 'currency', currency: code })`,
  which combines both correctly: `€ 6.50` in English, `6,50 €` in German.
- Conversion from the stored integer minor units: divide by `10^minor_unit`
  immediately before formatting, never earlier, and never in a way that
  round-trips through a float for arithmetic. All sums are computed on the
  integers.

## Text direction

Both supported languages are left-to-right. The markup nevertheless uses logical
CSS properties (`margin-inline-start` rather than `margin-left`) and sets `dir`
from the language, so a right-to-left language can be added later without
reworking the stylesheets.

## Translating the imprint and legal notes

The imprint and legal notes pages hold a single HTML snippet each, in whatever
language the operator supplies. They are not translated by the application, and
there is only one version of each. An operator who needs both languages puts
both into the one snippet.
