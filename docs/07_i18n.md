# 07 Internationalization and localization

## Supported languages

The set of languages is whatever catalogs the build contains. It is not fixed in
code, and nothing outside the catalog directory needs to change to add one.

The initial release ships two:

| Code | Language | Endonym  | Role                                                  |
| ---- | -------- | -------- | ----------------------------------------------------- |
| `en` | English  | English  | Source language and fallback. Complete by definition.  |
| `de` | German   | Deutsch  | Full translation shipped with the application.         |

Later releases may add more, and the application must not need modifying for
them to appear.

### The language registry

Each catalog declares its own metadata in a reserved `_meta` key:

```json
{
  "_meta": { "code": "de", "endonym": "Deutsch", "dir": "ltr" },
  "order.deadline.label": "Bestellschluss",
  "…": "…"
}
```

At build time the bundler globs `frontend/src/i18n/*.json` and generates a
registry module listing every catalog it found with its `_meta`. The language
selector in the title bar renders straight from that registry, showing each
language by its **endonym** — "Deutsch", not "German" — because a person looking
for their own language looks for its own name.

Consequences:

- Adding a language is: drop `fr.json` into `frontend/src/i18n/`, rebuild. It
  appears in the selector, in the `Accept-Language` matching and in the
  `doener_lang` cookie validation automatically.
- No list of languages exists anywhere else — not in the backend, not in the
  database, not in the UI component. A hardcoded pair of languages anywhere is
  a defect.
- When only one catalog is present, the selector is hidden rather than shown
  with a single option.

## Language selection

The interface language is resolved in this order, first match wins:

1. The `doener_lang` cookie, if it names a language present in the registry.
2. The browser's `Accept-Language` header, matched against the registry by
   primary subtag in the header's own quality order — `de-AT` and `de-CH` both
   resolve to `de`.
3. English.

"Present in the registry" is checked against the catalogs actually in the build,
so a cookie left over from an installation that had a language which was later
removed falls through to the next step instead of producing an empty interface.

Choosing a language from the title bar writes the cookie and re-renders without
a page reload.

## Where translation happens

Translation is a **frontend** concern. The backend does not localize.

- API responses carry stable machine-readable identifiers — error `code`,
  allergen `code`, tag `code`, contact type `code` — and the frontend maps them
  to display text.
- API error `message` fields are English developer-facing text. The frontend
  shows the translation for the error `code` and only falls back to `message`
  when no translation exists.
- Log output is English, always, regardless of the operator's locale.
- User-entered content — restaurant names, menu item names, descriptions,
  free-text modifications — is never translated. It is displayed as entered.

### Reference data names

**No seeded reference table stores a display name.** Each stores a stable
`code`, and the frontend translates it. Adding a language is one catalog file
and never a database migration.

| Table          | Catalog key prefix | Example key           |
| -------------- | ------------------ | --------------------- |
| `currency`     | `currency.`        | `currency.EUR`        |
| `allergen`     | `allergen.`        | `allergen.gluten`     |
| `additive`     | `additive.`        | `additive.colouring`  |
| `contact_type` | `contact_type.`    | `contact_type.phone`  |
| `tag` (seeded) | `tag.`             | `tag.vegan`           |

Columns that survive are the ones that are properties of the thing rather than
of a language: `currency.symbol`, `currency.minor_unit` and
`currency.minor_per_major`,
`allergen.reference` and `additive.reference` (their regulatory or conventional
numbers), `contact_type.render_as`, and every `sort_order`.

The dividing line is who created the row. Seeded rows are translated from the
catalog; rows a user creates at runtime carry their name in the database,
because no catalog can anticipate them. That is why `tag` keeps a `name` column
— it is used only for user-invented tags — and why restaurant, menu item and
category names are never translated at all.

#### Fallbacks

A code with no catalog entry falls back to the code itself, rendered in a
neutral style. This is legible for currencies, where `EUR` is universally
understood, and merely ugly for the rest — `gluten` instead of "Cereals
containing gluten". The catalog completeness check in CI is what keeps that from
happening in practice: a code present in the seed migrations with no matching
key in the English catalog fails the build.

#### What API consumers lose

An API consumer without the frontend's catalog now receives codes and nothing
else from `/allergens`, `/additives`, `/currencies` and `/contact-types`. That
is a real, accepted cost of this decision.

It is tolerable because the codes are self-describing English words chosen for
exactly that reason, the allergen and additive `reference` numbers map onto
published regulations, and third-party API use is not a focus of the first
release. If a consumer ever needs localized names, the answer is an endpoint
that serves the catalogs themselves — not name columns back in the tables.

#### Regulatory wording

The `allergen` entries, and to a lesser extent the `additive` entries, are legal
declarations rather than UI copy. Their catalog entries carry a comment naming
the regulation they come from, and they must not be reworded for tone, brevity
or house style the way an ordinary label can be.

## Catalog format

- One JSON file per language under `frontend/src/i18n/`, compiled into the
  bundle at build time. Nothing is fetched over the network at runtime.
- Keys are dotted and namespaced by area, e.g. `order.deadline.label`,
  `error.1003`, `allergen.gluten`, `additive.colouring`, `currency.EUR`,
  `contact_type.phone`, `tag.vegan`.
- Plural forms use the ECMA-402 `Intl.PluralRules` categories. A catalog
  supplies whichever categories its own language has — `one`/`other` for English
  and German, more for others — and the renderer asks `Intl.PluralRules` which
  one applies rather than assuming a fixed pair.
- A build-time check fails the build if **any** catalog is missing a key that
  exists in the English one. Extra keys in a translation are a warning. The
  check iterates the registry, so it covers languages added later without being
  changed.
- Interpolation uses named placeholders: `"{count} items from {restaurant}"`.

## Formatting

All formatting uses the browser's `Intl` API with the resolved interface
language as the locale.

| Value          | Rule                                                                                   |
| -------------- | -------------------------------------------------------------------------------------- |
| Dates          | `Intl.DateTimeFormat` with the interface locale. `en` → `Sep 10, 2026`, `de` → `10.09.2026`. |
| Times          | `Intl.DateTimeFormat`. `en` → 12-hour, `de` → 24-hour, as the locale dictates.          |
| Relative times | `Intl.RelativeTimeFormat` for deadline hints — "in 2 hours" / "in 2 Stunden".            |
| Weekdays       | `Intl.DateTimeFormat` weekday names, for opening hours.                                 |
| Numbers        | `Intl.NumberFormat`. Decimal and grouping separators follow the locale.                 |
| Money          | See below.                                                                              |

### Time zones

Every timestamp crosses the API as UTC (RFC 3339 with `Z`). The browser converts
to the viewer's local time zone for display, and converts back to UTC before
sending. The specification assumes restaurant and participants share one time
zone, so no time zone is ever displayed or stored alongside a timestamp.

Opening hours are wall-clock `time` values without a date and are displayed as
stored, without conversion.

### Money

Money is the one place where the interface locale does **not** decide
everything.

- The **currency** comes from the restaurant and never changes with the
  interface language. A restaurant priced in CHF shows CHF to a German-speaking
  and to an English-speaking user alike.
- The **number formatting** follows the interface locale.
- The symbol comes from the `currency` table's `symbol` column, the number of
  decimals from its `minor_unit` column, and what the currency divides into from
  its `minor_per_major` column.
- Rendering uses `Intl.NumberFormat(locale, { style: 'currency', currency: code })`,
  which combines both correctly: `€ 6.50` in English, `6,50 €` in German.
- Conversion from the stored integer minor units: divide by `minor_per_major`
  immediately before formatting, never earlier, and never in a way that
  round-trips through a float for arithmetic. All sums are computed on the
  integers. The divisor is **not** `10^minor_unit`: that is true of every
  currency but the Malagasy ariary and the Mauritanian ouguiya, which divide
  into five.

## Text direction

Both supported languages are left-to-right. The markup nevertheless uses logical
CSS properties (`margin-inline-start` rather than `margin-left`) and sets `dir`
from the language, so a right-to-left language can be added later without
reworking the stylesheets.

## Translating the imprint and legal notes

The imprint and legal notes pages hold a single HTML snippet each, in whatever
language the operator supplies. They are not translated by the application, and
there is only one version of each. An operator who needs both languages puts
both into the one snippet.
